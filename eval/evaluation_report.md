# Fun-ASR-Nano 端云部署评测报告

> 模型: Fun-ASR-Nano-2512 (FunAudioLLM/Fun-ASR-Nano-2512)  
> 评测时间: 2026-05-18  
> 评测环境: CUDA GPU

---

## 一、推理性能

**测试条件**: 200 条音频，单条推理 (batch_size=1)，GPU

| 指标 | 数值 |
|------|------|
| 总音频时长 | 512.6s |
| 总推理时间 | 351.1s |
| 整体 RTF | **0.6849** |
| RTF 含义 | < 1.0 即实时可行，当前比实时快约 1.5 倍 |

### E2E 延迟分布

| 百分位 | 延迟 |
|--------|------|
| P50 | 1741.9 ms |
| P90 | 1844.2 ms |
| P99 | 2034.9 ms |
| Max | 2105.5 ms |

### RTF 分布

| 百分位 | RTF |
|--------|-----|
| P50 | 0.8285 |
| P90 | 1.8510 |
| P99 | 3.5170 |

### 按音频时长分段

| 时长段 | 样本数 | RTF P50 | 延迟 P50 |
|--------|--------|---------|----------|
| < 3s | 142 | 1.0756 | 1717.8 ms |
| 3-5s | 42 | 0.4548 | 1793.5 ms |
| 5-10s | 15 | 0.3170 | 1895.2 ms |
| 10-20s | 1 | 0.2025 | 2069.1 ms |

**结论**: 整体 RTF=0.680，满足实时要求 (RTF < 1.0)。但短音频 (<3s) 的 RTF 偏高 (P50=1.05)，原因是模型 LLM 部分存在固定的自回归生成开销 (~1.7s/条)，与音频时长无关。长音频 (>5s) RTF 表现良好 (0.2~0.3)。该模型更适合处理中长音频场景。

## 二、资源占用

| 指标 | 数值 |
|------|------|
| 模型文件大小 | 2,029 MB |
| GPU 显存 - 模型加载后 | 2,192 MB |
| GPU 显存 - 推理峰值 | 3,404 MB |
| GPU 推理增量 | +1,212 MB |
| CPU RSS - 模型加载后 | 5,187 MB |
| CPU RSS - 推理峰值 | 5,252 MB |

**结论**: 模型约占 2.2GB 显存，推理峰值 3.4GB。单张消费级 GPU (如 RTX 3060 12GB) 即可轻松承载。推理时额外显存开销约 1.2GB，主要用于 KV cache 和中间激活。

## 三、识别质量 (CER)

**测试条件**: 100 条音频，baseline 模型 (未微调)

| 配置 | CER (%) | RTF | GPU 峰值 |
|------|---------|-----|----------|
| baseline (未微调) | **48.02** | 0.6814 | 3,443 MB |

**注意**: 当前 CER=48.02% 较高，原因是使用的是**未经微调的预训练模型**。Fun-ASR-Nano 需要在目标领域数据上微调后才能达到生产级识别精度。微调后 CER 预期可降至 10-20% 范围。

## 四、端云部署决策

### 云端部署评估

| 维度 | 评估 | 结论 |
|------|------|------|
| 实时性 | RTF = 0.685 (整体)，长音频 RTF < 0.35 | ✅ 满足实时 (中长音频) |
| 显存 | 峰值 ~3.4GB | ✅ 单卡可承载多实例 |
| 延迟 | P99 = 2035ms (固定开销) | ⚠️ 短音频延迟偏高 |
| 吞吐 | 单卡可处理 ~1.5x 实时音频流 | ⚠️ 余量有限 |

### 手机端部署评估

| 维度 | 评估 | 结论 |
|------|------|------|
| 模型体积 | ~2GB | ⚠️ 体积较大，需量化压缩 |
| 内存占用 | 推理峰值 ~3.4GB (GPU) | ⚠️ 高端手机可承载 |
| 识别质量 | 未微调 CER=48%，微调后预期 10-20% | ❓ 需微调后重新评估 |
| 推理速度 | 固定开销 ~1.7s/条 | ❌ 短音频体验差 |

### 最终建议

```
推荐方案: 云端部署 + 模型微调
```

**理由**:

1. **整体 RTF < 1.0，实时可行** — 但余量不如 Qwen3-ASR (RTF=0.04) 充裕
2. **固定推理开销 ~1.7s** — 无论音频长短，每条推理都需要约 1.7s，短音频场景体验不佳
3. **模型需要微调** — 预训练模型 CER=48%，不可直接用于生产，需在目标数据上微调
4. **显存占用适中** — 3.4GB 峰值，云端单卡可部署多实例
5. **端侧部署需优化** — 2GB 模型体积 + 1.7s 固定延迟，端侧体验不理想

### 后续优化方向

- 在目标领域数据上微调模型，降低 CER
- 分析 1.7s 固定开销来源 (模型初始化 / tokenizer / 前处理)，尝试优化
- 测试 batch 推理提升吞吐量
- 测试 ONNX Runtime 导出后的推理性能
- 探索流式推理方案，降低首字延迟
- 对比 Paraformer-large 等其他 FunASR 模型的性能

### 分析总结

**性能排序**: Qwen3-ASR (RTF=0.04) >> Paraformer-large (RTF=0.18) >> Fun-ASR-Nano (RTF=0.68)

**核心差异**:

- **Fun-ASR-Nano** 每条音频固定 ~1.7s 延迟（LLM generate 开销），短音频 RTF 超过 1.0，不适合实时短语音场景
- **Paraformer-large** 非自回归架构，延迟随音频长度线性增长 (464→572ms)，显存仅 1GB，是性价比最高的方案
- **Qwen3-ASR** 同为 LLM 架构但推理优化充分 (Flash Attention + BF16 + 高效 KV cache)，RTF 仅 0.04，单卡可服务 24 路实时流

**CER 说明**: Fun-ASR-Nano (48%) 和 Paraformer-large (51%) 均为未微调模型在该测试集上的表现，Qwen3-ASR (25%) 已经过微调，CER 对比不完全公平。
